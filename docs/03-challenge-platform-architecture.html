How the challenge platform fits together

Three zones: the browser app, Convex as the realtime backend, and outside services that Convex calls or that feed it. The browser never talks to the code runner directly, and there is no open web search. Research happens in a docs library you host yourself, so every page read stays inside the platform.

A submission, step by step

  1. User presses Submit. The browser calls the Convex action submit(code, lang, problemId) with the Clerk token attached.
  2. Convex verifies the token, checks the rate limit, and a mutation inserts a submissions row with status queued.
  3. The action loads the hidden test cases and posts code plus tests to the runner, with a callback URL (a Convex HTTP endpoint).
  4. The runner compiles once, runs every test in a fresh sandbox with no network, and posts results to the callback.
  5. The HTTP endpoint checks a shared secret and runs a mutation that writes the verdict, runtime and memory.
  6. Every browser subscribed to that submission, or to the match, updates instantly. In a duel, the opponent sees the test count, never the code.

A 1v1 duel, step by step

  1. Player joins the queue (a matchQueue row with their duel rating), or opens a friend's challenge link.
  2. A scheduled function pairs players by rating band and widens the band the longer someone waits.
  3. It creates a matches row in lobby, picks a problem neither player has solved, and keeps it hidden.
  4. The server sets the start time. At start the state flips to active and the problem becomes readable.
  5. Each submission writes a matchEvents row. Both HUDs subscribe to the match and show progress live.
  6. First full pass wins. A mutation finishes the match, updates Glicko-2 ratings, and queues a similarity check on both solutions.

Research: the docs library

No embedded Google and no iframes. Google's own search APIs no longer cover the whole web for new customers, most docs sites refuse to be framed, and an iframe hides which page someone reads and where their links lead. Hosting the docs yourself fixes all three.

  1. A scraper job (reusing DevDocs' open-source scrapers) downloads each doc set for a specific language version, for example Python 3.13, and cleans the HTML.
  2. It imports the pages into a docPages table (language, version, path, title, body, license line) with a Convex search index on the text.
  3. The research panel calls searchDocs and getDocPage. Links inside a page point to other stored pages; external links are disabled or opened in a logged new tab.
  4. Before returning anything, the query checks the attempt's mode. Docs a mode doesn't allow are never sent to the browser, so the rule can't be bypassed in the client.
  5. Each opened page writes a docViews row (user, attempt, page, time spent). The results view shows it as "solved using 3 doc pages".
  6. When a runner language is upgraded, the job runs again for the new version. That is roughly once a year per language, not a recurring crawl.

Creating a problem

Creating problems is a paid feature (Pro, or invited top players in a creator program).

  1. A creator writes the statement, test cases (sample and hidden) and a reference solution in any supported language. By default every language may solve it; the creator can restrict languages.
  2. The platform runs the reference solution in the runner. It must pass every test, ideally alongside a second solution in another language. Time limits get a per-language multiplier.
  3. The problem enters beta in practice only. Users who solved it vote on difficulty and quality and can file issue reports.
  4. After enough solves, good ratings and a reviewer sign-off it becomes approved and can appear in ranked duels.
  5. Difficulty is then recalculated from real results: solve rate, attempts, time taken and the ratings of solvers versus non-solvers.
  6. Discussion unlocks for each user only after they solve the problem. Contests use fresh problems nobody has seen.

Running a ninjathon

Creating ninjathons is paid: Pro for small private events, the Organization plan for public, branded ones.

  1. An organizer creates an events row: dates, rules, judges, prizes, and an entry type of free, paid or invite.
  2. Participants register in registrations. For paid entry, the row is confirmed only by the payment webhook, never by the browser.
  3. Teams form and submit projects before the server-side deadline; submissions lock at that time.
  4. Judges score against a rubric; results and rankings publish when judging closes.
  5. Paid entry (later) pays organizers through Stripe Connect minus a platform fee. Check local rules on paid entry with prizes before launching it.

Plans and entitlements

One entitlements row per user or organization (plan, quotas, renewal date). Only the payment webhook writes it, and every paid feature checks it inside Convex, never in the browser.

FreeAll exercises, ranked duels, contests, rankings and leaderboards, docs library, basic profile with free and earned themes, a few AI hints per day, joining ninjathons.
ProCourses and tutorials, unlimited AI coach, deep analytics and duel replays, problem creation, private ninjathons, full profile customization.
OrganizationPublic branded ninjathons, hiring challenges, candidate reports, classes and assignments.

Never paid: rating, ranked games, leaderboard placement, or anything that helps win a duel.

Profiles

  1. A profiles row stores a template id and validated theme values: colors, font choice, banner and background image, section order.
  2. Users never write CSS or HTML. The server validates values, including a text contrast check, and your code renders the page.
  3. Images go to Convex file storage with size limits and a content check before going public.
  4. Rating, rank, solved count and duel record render in a fixed platform block that no theme can restyle or hide.
  5. Free users edit the basics and unlock themes by playing; Pro users get the full template library and custom styling.
Guardrail · non-negotiable

Every check happens in Convex, before the data leaves the server

Next.js decides what to show. Convex decides what to send. Middleware, route protection, hidden buttons and client-side plan checks are for user experience only and are never treated as security. If a Convex function returns data, it must already have checked who is asking and what their plan allows.

  • Wrappers instead of raw functions. All public functions are built from userQuery, proQuery, proMutation and similar wrappers that check identity and entitlements first. A lint rule blocks importing raw query and mutation outside convex/lib.
  • Actions go through internal queries. Actions have no database access, so they call an internal query that runs the same check before calling the runner or the AI coach.
  • No Pro content in pages. Course pages are never statically generated with lesson text, and locked content is never sent blurred or hidden. Public pages show title, outline and the free preview module only.
  • One writer for plans. Only the payment webhook writes entitlements. No function callable from the browser can change a plan.
  • Test the denial path. Each Pro function gets a test that calls it as a free user and expects it to throw.
// convex/lib/functions.ts
export const proQuery = customQuery(query,
  customCtx(async (ctx) => {
    const user = await requireUser(ctx);
    const plan = await ctx.db.query("entitlements")
      .withIndex("by_user", (q) => q.eq("userId", user._id))
      .unique();
    if (!plan || plan.tier === "free" || plan.expiresAt < Date.now())
      throw new ConvexError("PRO_REQUIRED");
    return { user, plan };
  }));

// convex/courses.ts
export const getLesson = proQuery({
  args: { lessonId: v.id("lessons") },
  handler: async (ctx, { lessonId }) =>
    ctx.db.get(lessonId),  // runs only after the check
});

Uses customQuery and customCtx from the convex-helpers package. Free preview modules use a separate userQuery that checks the lesson's isPreview flag.

One Next.js app, three route groups

(marketing)/, /features, /pricing, /blog. Statically generated, metadata, Open Graph images, sitemap, structured data, little JavaScript.
(public)/problems/[slug], /u/[username], /leaderboard, /contests/[id]. Server-rendered for search engines; turns into the solving view for signed-in users. Most SEO traffic comes from here.
(app)/dashboard, /duel/[id], /solve/[slug], /courses, /settings. Behind sign-in, client-heavy, live Convex subscriptions. Monaco and the duel HUD load only here.

Split into a monorepo (for example apps/web, apps/app, packages/ui, one convex folder) only when a marketing team needs its own CMS and deploys, or build times start to hurt. Keeping shared components in their own folder from day one makes that split cheap.
