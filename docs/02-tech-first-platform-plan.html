Tech-first plan: practice, duels, contests

Decided since: Research panel Free, Pro, Organization Problem creation Ninjathons Profiles Security App structure & guardrail Play modes Territory World Conquest Leaderboard Profile screens Problem library Later

Good choice. Tech gives you one grader type (code runs against tests) to get right before adding others. Here's how I'd shape it.

Features, in build order

  1. Problem library and solo practice: problem view, editor, results, research panel
  2. Duels and multiplayer battles: the Conquistador part, and your most distinctive feature
  3. Contests: scheduled, ranked, many people solving the same set
  4. Learning paths: "Learn Rust through 40 problems," with the AI coach
  5. Hackathons: teams, repos, and judges, which is a different beast from auto-graded problems

Duels should come before contests. Contests need a crowd, but a duel only needs two friends and a link. That's also how the platform spreads.

Duels, Conquistador-style

The Conquistador loop works for code: short rounds, visible stakes, and conquering territory from your opponents. Some formats to consider:

  • 1v1 race: same problem, first to pass all hidden tests wins. The simplest mode, so build it first.
  • Territory map: 3 players on a map, each region holds a problem, and whoever solves it first claims it. You can attack an opponent's region by solving a harder problem there. This mode is your identity.
  • Battle royale: 8 to 20 players, several rounds, and the slowest drop out each round.
  • Twist modes (CodinGame's Clash of Code proves these work): shortest code wins, or "reverse" mode where you only see input/output examples and have to infer the problem.
  • Challenge a friend: send a link and you're in a lobby.

Technically, Convex fits duels well:

  • Server-authoritative match state: lobby, countdown, active, finished. The server owns the clock, not the client.
  • Problem hidden until start: it's revealed only when the match goes active. Draw it from a pool neither player has solved before.
  • Live opponent progress: show things like "Opponent: 7/12 tests passing, 3 submissions" through Convex subscriptions, but never their code.
  • Matchmaking: a queue table plus a scheduled function that pairs people by rating band and widens the band over time.
  • Ratings: Glicko-2, with separate ratings for duels and contests.

The code runner

This is where the real engineering is.

Judging model. You have two options:

  • stdin/stdout (Codeforces style): the program reads input and prints output. Works in any language with no extra effort per language.
  • Function signature (LeetCode style): the user fills in twoSum(nums, target). This is nicer for users, but you need a generated test harness for every language on every problem.

My recommendation is to start with stdin/stdout, store test cases as language-agnostic JSON, and add function-signature problems later with a harness generator.

Decided 3 Oct 2026: both modes from V1. Each problem is either function mode (generated starter code and driver) or full-program stdin/stdout mode. See notes/decisions.md.

Sandbox. Judge0 self-hosted is the fastest path, since it supports dozens of languages. Run it on its own VM, separate from everything else. The non-negotiables:

  • No network access
  • CPU, memory, and time limits
  • Output size cap
  • A fresh sandbox for every run

Check your host's cgroup setup before committing to Judge0, because it's picky about host configuration.

Run vs Submit.

  • Run checks only the sample tests and should feel instant.
  • Submit checks all hidden tests.

Rate-limit both. In a duel, people will spam Run.

Latency. Duels depend on it. Keep warm runners, compile once and then run all tests, and queue with priority (duel submissions ahead of practice).

Architecture

Next.js (Monaco editor, research panel)
   │  Clerk auth
   ▼
Convex ── queries/subscriptions: problems, matches, leaderboards, presence
   │  action: submit(code, lang, problemId)
   ▼
Runner service (Judge0 on isolated VM)
   │  webhook with results
   ▼
Convex mutation → updates submission → UI updates live for both players

Core tables

  • users: Clerk id, ratings per mode
  • problems: statement, difficulty, tags, author, status (beta or approved)
  • testCases: problem, input, expected output, sample or hidden
  • submissions: user, problem, language, code, verdict, runtime, memory, integrity signals, match (optional)
  • matches: mode, state, participants, problem set, start and end times, map state for territory mode
  • matchEvents: submitted, solved, captured region; drives the live feed
  • contests: holds problem sets, schedule, and registrations; can come later

Anti-cheat for duels

Duels are harder to cheat in than solo practice:

  • The time window is short.
  • The problem is unseen until the match starts.
  • Both solutions can be compared automatically afterwards: similarity between opponents, and similarity to known public solutions.

Add the tab-leave and paste signals from before and show a trust indicator. Flag suspicious games for review rather than punishing automatically.

Languages

Launch with 4 or 5: Python, JavaScript/TypeScript, Java, C++, and C#. Learning paths per language later are mostly a content problem, not a technical one.

Two questions that shape the next step:

  • Judging model: stdin/stdout for the MVP, or is the LeetCode-style function experience important to you from day one?
  • Duel formats: should the territory map be in the first version, or do we ship the 1v1 race first and add the map once matches work?
Update · 26 Sept 2026

Research panel: a hosted docs library

Decided after the brainstorm above: no embedded Google, no iframes, and no web search API in the MVP. The research panel becomes a docs library the platform hosts itself.

Why not Google or iframes.

  • Google.com refuses to load inside another site's iframe.
  • Google's Custom Search JSON API is closed to new customers and ends for existing ones on January 1, 2027. New Programmable Search engines are limited to 50 chosen domains.
  • Many docs sites also block iframes, and a site can change that at any time.
  • Inside an iframe you can't see which page someone reads, and you can't stop links leading to other sites. Per-page tracking and "official docs only" rules would be impossible.

How the docs library works.

  • A scraper job, reusing DevDocs' open-source scrapers, imports doc sets with open licenses (MDN, Python docs, cppreference, Rust docs and similar) with a source and license line on each page.
  • Docs are pinned to the same language version the runner uses. The job runs again only when a runner language is upgraded, roughly once a year per language.
  • Pages live in a Convex docPages table with a search index. The panel searches and reads them through Convex queries.
  • Every page opened is logged as a docViews row, so results can show "solved using 3 doc pages".

Docs policy per mode, enforced by the query on the server:

  • Practice: all doc sets, plus a logged "open in new tab" button for anything else.
  • Duels: official references only, or no docs. Still open.
  • Hard-mode contests: no docs, with a separate no-docs leaderboard.
  • AI coach (later): hints point to exact doc sections instead of giving code.
  • Desktop app (later): its own web view can show any site, including Google, and log every URL, so full browsing becomes possible there.

Free, Pro and Organization

The rule: never sell an advantage in competition. Charge for teaching, for things that cost money to run, and for things organizations need.

Free

  • Every exercise in the library, in any language
  • Ranked duels, matchmaking, contests, ratings and all leaderboards (global, per language, per country, friends)
  • The docs library in every mode
  • Basic stats and rating history
  • A basic profile, free themes, and themes earned by playing
  • A few AI hints per day
  • Joining ninjathons

Pro

  • Courses and tutorials: lessons, structure, progress tracking, the course's AI coach, certificates. The first module of each course stays free as a preview.
  • Unlimited AI coach
  • Deep analytics: weak topics, speed versus your rating band, duel replays
  • Creating problems
  • Creating small private ninjathons
  • Full profile customization

Organization

  • Public, branded ninjathons and hiring challenges
  • Candidate reports with similarity checks
  • Classes, assignments and class leaderboards for universities and bootcamps
  • Priced per event or per seat

Never paid: rating, extra ranked games, leaderboard placement, extra Run attempts in a duel, ads in the editor or duel view.

Changed from earlier: premium problem sets are dropped, because every exercise is free. Interview prep becomes a course instead. Courses only point to exercises in the public library, so free users can still solve those exercises; they pay for the teaching around them.

Launch timing: launch fully free, add Pro once people hit the free AI limit, and run one company-hosted ninjathon early as a pilot.

Update · 26 Sept 2026

Problem creation and review

  • Paid feature: Pro users create problems. Top-ranked players can also be invited into a creator program. Creators can earn a revenue share on premium courses later.
  • Seed the library yourself at launch, a few hundred problems, since paid creation means fewer community problems.
  • Language-agnostic by default: statement, test cases and a reference solution in any language; everyone can solve it in any supported language. Creators can restrict languages when needed.
  • Validation: the reference solution must pass every test in the runner, ideally with a second solution in another language. Time limits get a per-language multiplier.
  • Language-specific problems (Rust lifetimes, a JavaScript debounce) come later with the function-signature harness.
  • Beta review: only users who solved it vote on difficulty and quality. Approval needs enough solves, good ratings and a reviewer sign-off.
  • Difficulty after approval is recalculated from real results: solve rate, attempts, time taken, and solver versus non-solver ratings.
  • Comments: issue reports open to everyone; discussion unlocks only after solving; comments closed during duels and contests; flagging and reputation limits for moderation.
  • Ranked use: community problems start in practice. Ranked duels use approved problems; contests use fresh, unseen problems.

Update · 26 Sept 2026

Security

  • Runner: separate VM, fresh sandbox per run, no network, unprivileged user, read-only filesystem, limits on CPU, memory, processes, time and output, and alerts on load spikes. Results only via a signed webhook.
  • Convex: every public function checks the caller. Hidden tests are read only by internal functions. Duel problems stay hidden until the match is active. Opponent progress returns counts, never code. Ratings and verdicts change only in internal mutations. The server clock decides all timing.
  • Rankings: provisional ratings for new accounts, verified login for ranked play, detection of repeated one-sided pairings, rate limits on Run and Submit.
  • User content: sanitized markdown; new problems stay in practice until approved.
  • Payments: an entitlements table written only by the payment webhook; every paid feature checks it on the server.
  • AI coach: server-side quotas and hints only, guarded against prompts asking for full solutions.
  • GDPR: disclose tracking, collect only what you use, delete raw behavior events after a set period (for example 90 days), keep aggregated trust scores, support account deletion.
Update · 26 Sept 2026

One Next.js app, and the Convex guardrail

One app with three route groups:

  • (marketing): home, features, pricing, blog. Statically generated with metadata, Open Graph images, sitemap and structured data.
  • (public): problem pages, public profiles, leaderboards, contest results. Server-rendered for search engines, and the same page becomes the solving view for signed-in users. This is where most SEO traffic will come from, and the main reason to keep one app.
  • (app): dashboard, duels, solving, courses, settings. Behind sign-in, client-heavy, live Convex subscriptions.
  • Split into a monorepo only when a marketing team needs its own CMS and deploys, or build times hurt. Keep shared components in their own folder from the start.

Guardrail: every check happens in Convex, before the data leaves the server. Next.js decides what to show; Convex decides what to send. Middleware and route protection are for redirects and user experience only, never for security.

  • All public Convex functions are built from wrappers (userQuery, proQuery, proMutation) that check identity and entitlements first. A lint rule blocks raw query and mutation outside convex/lib.
  • Actions call an internal query that runs the same check before calling the runner or the AI coach.
  • No Pro content in pages: course pages are never statically generated with lesson text, and locked content is never sent blurred or hidden. Public course pages show the title, outline and free preview module.
  • Only the payment webhook writes entitlements.
  • Every Pro function has a test that calls it as a free user and expects it to fail.
  • Not fully preventable: paying users copying text or sharing accounts. Limit concurrent sessions and accept the rest.

Play modes: find a match or challenge someone

  • Navigation: "Play modes" in the sidebar is a dropdown listing 1v1 race, Territory, Battle royale, Twist modes, Weekly contests, Ninjathons and Create problems (Pro). No second sidebar.
  • Mode page layout: title and description, rule tiles, two large choice cards, the panel for the chosen card, "How it works" in four steps, and a "Who can do what" table (Free, Pro, Organization).
  • Two ways into every match mode:
    • Find a match (ranked): pick a language, get matched by duel rating. The rating range widens the longer you wait.
    • Challenge someone (unranked): invite players by username, pick from friends and recent opponents, or copy an invite link. Set difficulty, language and time limit. Start unlocks once enough players accept.
  • Challenges never change ratings, so friends can't trade wins to boost each other.
  • Incoming challenges appear at the top of the page with Accept and Decline, including the settings and when the invite expires.
  • Live signals build confidence that a match will happen: players online per mode, expected wait, friends online.
  • Button hierarchy: the two choice cards have equal weight. The black primary button is kept for the action that completes the flow inside the panel (Find a match, Send invite, Start).
  • Username invites show clear errors: unknown player, yourself, duplicate invite, full lobby.
Update · 27 Sept 2026

Territory

  • Players: minimum 3, maximum 6. With 2 players it would just be a 1v1; above 6 a 30-minute match gets chaotic.
  • Map: hex regions. 37 regions for 3 to 4 players, 61 for 5 to 6. Each player starts with a home base on the edge.
  • Region values: Easy on the edge (+1), Medium (+2), Hard (+3), and a Core in the center (+5). The 37-region map totals 65 points.
  • Claim: solve the problem of an empty region next to one you hold.
  • Attack: solve a problem one level harder to take a rival's region next to yours.
  • Home bases can't be captured, so nobody is knocked out early.
  • 60-second shield on newly captured regions, so regions don't flip back and forth.
  • Winning: first to more than half the points (33 of 65), or the most points when the 30 minutes run out.
  • Screen: map in the center, reachable regions tinted, a score bar with a 50% marker, the selected region's problem and action on the right, and a live match feed. In the real app, Claim or Attack opens the editor next to the map.
  • Ranked through Find a match, unranked through challenges, like 1v1.
Proposal · 27 Sept 2026

World Conquest (world map mode)

A long-running world map where players conquer regions for their country by solving problems, without walking anywhere. It's closer to a season than a match, so it should be its own mode rather than a Battle royale.

  • Country from the profile, not GPS. No location tracking and no privacy issue.
  • Season-based: 2 to 4 weeks. Players join whenever they want; each solve adds influence for their country in a region, and the region flips when another country's influence overtakes it.
  • Attack range: regions next to anything your country already holds, so geography matters.
  • Fair for small countries: a daily cap per player, and influence averaged per active player instead of summed.
  • Unranked, with generated problems: regions serve randomized variants, since problems stay up for days. Season rewards and badges instead of rating.
  • Stylized hex world, not real borders, to avoid disputed borders on a coding platform.
  • Battle royale stays as the short elimination mode (8 to 20 players, rounds, about 15 minutes).

Leaderboard

  • Fully free. Pro only adds analytics about your own position.
  • Boards: Duels, Contests, This week (rating gained in 7 days), Hard mode (no docs), Creators. Solve counts and streaks stay on profiles, since they measure activity rather than skill.
  • Scopes: Global, Country, Friends, My class. Filters by language and tier; seasons can come later.
  • Your position pinned at the top (rank, top %, tier, weekly change), with "Jump to me" showing the 5 players above and below you.
  • Rating distribution histogram with tier bands and a "you are here" marker.
  • Rows: rank with daily change, player and country code, tier, rating, games, win rate, main language, 7-day sparkline.
  • Trust rules: hidden until 10 ranked games, hidden after 30 days inactive (no rating decay), games under review don't count, ties go to whoever reached the rating first, players can hide their country.
  • Technical: a scheduled Convex job rebuilds a leaderboardSnapshots table every few minutes; friends and class boards are computed live; your own row reads live data.
