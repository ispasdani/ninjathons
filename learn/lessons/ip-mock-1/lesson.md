Time for a mock interview: one medium problem, 30 minutes, start to finish, as if someone were watching. Reading about the process only goes so far; doing it under a clock is what makes it automatic.

## Set up

- Set a timer for **30 minutes** before you open the problem. Use your phone, or the clock in the corner of your screen.
- Close everything else. Use the library's Docs tab if you need a reference, as you could ask an interviewer, but nothing else.
- Talk out loud, or type your thinking as comments in the editor. Nobody's listening, but the habit is the point.

## Follow the steps

1. **Understand (3 min).** Restate the problem in a comment. Write two small examples, one where the answer is `true` and one where it's `false`, and work them by hand.
2. **Plan (5 min).** Write the plan as comments: what you'll track, how you'll loop, the complexity. For this problem, think about how many separate "places" each value has to be unique in, and how to find each place quickly.
3. **Code (15 min).** Write it under the comments. Keep names clear.
4. **Test (5 min).** Before pressing Run, trace your examples by hand. Then Run. Then think of one case that could break it (a clash that's only in a box, not in a row or column), and check it.
5. **Wrap up (2 min).** Write the time and space complexity as a final comment.

## Afterwards: review honestly

When the timer goes off, stop, and score yourself:

| | Yes / no |
|---|---|
| Did I restate the problem and check examples before coding? | |
| Did I write the plan before the code? | |
| Did I find my own bugs before Run told me? | |
| Did I finish within the time? | |
| Could I state the complexity and why? | |

Whatever you said no to is what to practise next. If you didn't finish, finish it now without the timer, then try a second problem from the library tomorrow, timed again. Two or three mocks a week for a few weeks makes a bigger difference than any amount of reading.
